# CLAUDE.md - Tower Defense (Godot 4.3+)

## What this is
Top-down 2D casual-fantasy tower defense. Art is generated by Python/Pillow scripts (outside this folder) and exported into `assets/` + `data/`. This Godot project turns the art into a **playable game**. Goal: finish the milestones in `GAME_TASKS.md`, in order, keeping the game runnable after every step.

## Hard rules
- **Godot 4.3+**, GDScript 4, 2D only. Renderer GL Compatibility. Viewport 1280x768, stretch `canvas_items`, keep aspect.
- **Do not edit or regenerate PNGs in `assets/`.** They are generated outputs. If the game needs new art (new effect, icon, UI skin, monster, tower, map tiles), write it into `ART_REQUESTS.md` (what, size, frames, names) and use a simple placeholder (ColorRect / StyleBoxFlat / existing sprite) until the art arrives.
- Perspective is true top-down. Art tile 32 px, **logical grid cell 64 px**. Tower footprint 1x1 cell (64 px); 2x2 (128 px) must stay supported by the grid code.
- **Keep layers separate:** grid logic (`grid_manager.gd`, data only) / grid rendering (`grid_renderer.gd`) / placement overlay (`placement_layer.gd`) / tiles (Ground, Water, Path TileMapLayers). Hiding the grid or changing placement state must never touch the tile layers. Grid logic must work with the grid hidden.
- Towers: fixed BASE layer + rotating HEAD layer (art faces EAST, pivot = frame centre). Monsters: 4 directions (E,S,W,N). Sprite names/fps/frames are documented in `data/*.json` and `README.md`.
- Gameplay numbers live in data files (`data/*.json`, later `Resource` files), never hard-coded in scripts. Current numbers are PLACEHOLDERS - replace them with tuned values.
- Use `preload` constants instead of `class_name` dependencies. Typed GDScript where practical, snake_case, 4 spaces (or tabs) consistently per file, signals for events, no `get_node` chains across scenes if a signal or export var works.
- UI: `Control` nodes + a `Theme` resource + containers/anchors (desktop and mobile friendly). No pixel-positioned UI except prototypes.

## How to verify (adapt the executable name: `godot`, `godot4`, or the full path to the Godot binary)
Run `godot --help` once to confirm flags, then use:
- Import assets once: `godot --headless --path . --import`
- Smoke test (loads the main scene, runs ~600 frames, then quits; look for SCRIPT ERROR / Parser Error lines): `godot --headless --path . --quit-after 600`
- Parse-check one script: `godot --headless --path . --check-only --script res://scripts/<file>.gd`
- Static asset/data check (needs Python): `python3 ../04_SOURCE_SCRIPTS/validate_godot_project.py` (edit its `GD` path if the folder moved).
After every change: run the smoke test, fix every error and warning you introduced, then commit.
Visual or feel problems cannot be seen headless: describe exactly what the user should check by running the game (F5) and ask for feedback.

## Working agreement
- Work **one milestone at a time** from `GAME_TASKS.md`. Start each with a short plan; finish with: what changed, how it was verified, what the user should test by hand.
- Small commits with clear messages (`git init` if not a repo). Never rewrite or delete user files without asking.
- Do not invent facts about files: read the code first. Prefer extending existing scripts over rewriting them.
- Keep `README.md` (controls, layout) and `GAME_TASKS.md` (check boxes) up to date.
